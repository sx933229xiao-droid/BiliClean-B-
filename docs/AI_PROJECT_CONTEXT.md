## 2. 产品目标与不可破坏的设计决定

### 2.1 核心目标

BiliClean 的目标是减少 B 站网页中的低价值、攻击性、性暗示、性物化、性羞辱、引战、广告引流、低信息量评论，以及不符合用户阈值的视频卡片，同时默认关闭视频弹幕。

产品强调：

- 本地运行；
- 不接管 B 站登录；
- 不读取或上传 Cookie、密码和账号数据；
- 不自动点赞、投币、收藏、关注、举报、评论或发弹幕；
- 不使用远程代码、远程模型、遥测或广告 SDK；
- 尽量不破坏 B 站原有视觉布局；
- 过滤结果不在页面上制造额外噪音。

### 2.2 已确定的交互原则

| 场景 | 必须保持的行为 |
| --- | --- |
| 评论命中 | 直接隐藏整条评论，不显示原因、占位符或“查看一次”按钮 |
| 视频卡片命中 | 直接隐藏卡片，让 B 站原生网格或列表回流，不留下空白占位 |
| 误伤排查 | 通过扩展弹窗的“恢复本页内容”处理，不在网页内容区域插入提示 |
| 评论初次加载 | 首批最多 50 条评论先暂存，再合批判定；当前超时为 1.2 秒 |
| `@` 互动评论 | 默认屏蔽；只有可见字数 **大于 50** 且点赞数 **大于 100** 时保留，两个条件必须同时满足 |
| 低播放量视频 | 默认过滤播放量低于 50,000 的视频 |
| 短视频 | 默认过滤时长低于 60 秒的视频 |
| 弹幕 | 进入视频时默认关闭；默认允许用户在当前视频手动重新开启，进入下一视频后再关闭 |
| 统计 | 默认只在本地累计“屏蔽评论数”和“屏蔽视频数”，不保存正文、标题、网址或用户信息 |
| 默认模式 | 标准模式 |

### 2.3 当前明确不在 v0.1.4 范围内的内容

- 动态页过滤；
- 用户空间页过滤；
- 评论图片 OCR；
- 本地或云端 AI 语义分类；
- 服务器端服务与账号同步；
- 移动端 App 或真正的第三方 B 站客户端；
- 对 B 站账号服务器端弹幕设置进行修改。

当前内容解析器会收集评论图片 URL，但后续没有消费这些数据，因此这只是未完成的接口痕迹，不能对外宣称已经支持图片识别。

### 5.3 运行数据流

1. 内容脚本启动后向后台读取完整状态。
2. 根据 URL 绑定视频页、首页或搜索页适配器。
3. 适配器通过 DOM 选择器发现评论或视频卡片并解析字段。
4. 规则引擎先处理白名单/黑名单，再处理自定义规则、内置类别和阈值。
5. 渲染器把命中元素静默隐藏，并向后台批量上报新增过滤数量。
6. 设置变化通过 `chrome.storage.onChanged` 传给内容脚本；内容脚本销毁当前适配器、恢复页面，再按新状态重新绑定和扫描。
7. SPA 地址变化由 300 毫秒轮询加 `popstate/hashchange` 检测，并触发重新绑定。

以下结论来自 v0.1.4 代码本身，不依赖 B 站当前 DOM，可以直接建立 Issue 和修复任务。

### P0-1（已完成）：恢复完整源码、构建与测试工程

**证据**

**影响**

- AI 容易直接修改构建产物；
- 默认值和校验逻辑已重复出现在后台、内容脚本和设置页，容易只修一份；
- 无法可靠重建相同安装包；
- 无自动化回归，后续 B 站 DOM 适配容易反复损坏；
- 对开源项目和 Codex for Open Source 申请不利。

**完成状态（2026-08-19）**

- 已恢复 24 个 ESM JavaScript 源码模块；
- 已增加开发、构建、检查、测试和打包命令；
- `dist/` 可从源码与静态资源重新生成；
- 已为规则引擎、解析器、默认值和状态迁移建立单元测试；
- 发布包由脚本生成，不再手工拼装；
- 尚需由用户把本恢复工程提交到 GitHub 默认分支。

**验收条件**

在全新环境中按照 README 的命令，可以从源码生成结构和功能一致的 v0.1.4/v0.1.5 安装目录，并通过全部测试。

### P1-1：净化模式不是完整预设，严格模式设置会泄漏到其他模式

**静态证据**

`applyCleanModePreset` 只在进入 `strict` 时修改：

- `lowLikeEnabled = true`
- `maxLowLikeCount = Math.max(1, 当前值)`
- `requireCombinedWeakSignals = false`

切回 `standard` 或 `light` 时只改变 `mode`，不会恢复这些字段。

**实际后果**

用户进入严格模式后再切回标准或轻度，低点赞评论仍可能继续被直接过滤。并且如果用户之前把阈值改成 100，进入严格模式后仍保留 100，而安装说明写的是严格模式自动使用“点赞数 ≤ 1”。

**建议修复**

先明确模式语义，建议采用以下之一：

1. 真正的完整预设：每次切换模式都原子设置类别、低赞、等级、组合信号和宽限期；自定义模式才保存用户细调值。
2. 模式只控制内容类别：删除进入严格模式时偷偷修改低赞字段的副作用，并让低赞设置始终独立。

当前 UI 和安装说明更接近方案 1。无论采用哪种方案，弹窗与完整设置页必须调用同一份共享逻辑。

**验收条件**

- 标准 → 严格 → 标准后，最终行为与首次标准模式一致；
- 严格模式阈值和宽限期与文档完全一致；
- 快速切换模式不会因异步保存顺序导致旧设置覆盖新设置；
- 有单元测试覆盖四种模式的完整状态矩阵。

### P1-2：规则动作字段对用户无效，UI 与真实行为冲突

**静态证据**

设置页允许规则动作选择“折叠、模糊、隐藏”，规则引擎也保存 `collapse/blur/hide`。但：

- `FilterRenderer.applyComment` 会把任何非 `show` 结果强制改为 `hide`；
- `FilterRenderer.applyVideoCard` 也会把任何非 `show` 结果强制改为 `hide`；
- 评论规则计算还以 `defaultAction: hide` 作为最强起点，因此较弱动作不会生效。

**实际后果**

用户选择“模糊”或“折叠”后仍得到隐藏，形成明确的功能欺骗；无用字段也增加状态迁移和维护成本。

**建议修复**

根据已经确定的“静默隐藏”产品原则，优先选择：

- 从规则表单移除动作选项；
- 新规则统一保存为 `hide`；
- 导入旧规则时把旧动作安全迁移为 `hide`，或仅保留兼容读取；
- 删除未使用的模糊样式和无效动作复杂度。

如果未来确实要重新支持模糊/折叠，必须先征得用户同意，因为这会改变当前产品原则和网页观感。

**验收条件**

界面文案、导出 JSON、运行时行为三者一致，不再出现可选择但不生效的动作。

### P1-3：“不允许本视频手动开启弹幕”目前不能实现预期行为

**静态证据**

弹幕控制器初次关闭弹幕后停止重试。用户点击弹幕开关时，点击监听器只有在 `allowManualEnableForCurrentVideo === true` 时才记录“当前视频允许打开”；当该值为 `false` 时，代码没有再次调用关闭逻辑，也没有持续监听开关状态。

**实际后果**

关闭“允许本视频手动开启”后，用户仍可手动打开弹幕，并且扩展不会自动关回去。

**建议修复**

- 用户点击后读取到弹幕开启，且不允许手动开启时，立即安排一次可靠的关闭与验证；
- 同时监听播放器 DOM/开关状态变化，避免只靠有限次数的启动重试；
- 区分扩展主动点击与用户真实点击，防止循环；
- 不要修改 B 站账号的服务器端弹幕偏好。

**验收条件**

- 允许手动开启：用户打开后，本视频保持开启；切到另一视频后重新关闭；
- 不允许手动开启：用户打开后会被自动关闭；
- 播放器延迟超过当前约 10 秒才出现时，扩展仍能关闭弹幕；
- SPA 切视频、网页刷新、分 P 切换均有测试。

### P1-4：“恢复本页内容”后，“重新扫描”无法重新过滤同一批元素

**静态证据**

“恢复本页内容”会将元素加入 `revealed` WeakSet。之后即使调用 `rescan()`，`applyComment/applyVideoCard` 仍因元素存在于 `revealed` 中而直接恢复，不会重新隐藏。`revealed` 在适配器重绑和路由变化时也没有显式重置。

**实际后果**

- 用户点击“恢复本页内容”后再点“重新扫描”，同一 DOM 元素不会恢复过滤；
- 页面复用/虚拟化同一元素时，未来内容也可能继续被放行；
- 按钮语义互相冲突。

**建议修复**

- 为“本页临时显示”建立明确、可清除的会话状态；
- `BC_RESCAN_PAGE` 应清除临时放行状态后重新判定；
- URL 代表新视频或新页面时应清除上一页的临时放行；
- 如果用户期望“恢复直到刷新”，则应禁用或重命名“重新扫描”，避免矛盾。

**验收条件**

- 恢复后页面内容立即出现；
- 点击重新扫描后，仍符合规则的同一元素再次被隐藏；
- 进入新视频或新搜索结果页后不继承旧页面的临时放行。

### P1-5：设置页的“本地诊断信息”开关没有实际诊断实现

**静态证据**

`diagnosticsEnabled` 只出现在默认值、校验、设置读写和 UI 中，没有任何诊断记录、查看、导出或清除逻辑。

**实际后果**

用户看到一个看似可用但没有效果的开关；隐私说明也无法准确解释它到底记录什么。

**建议修复**

短期优先从 UI 隐藏或标记为“尚未实现”。如果要实现，应只保存有限、可清除、默认关闭的本地适配信息，例如：页面类型、未识别字段数量、选择器命中计数和错误代码；不得保存评论正文、视频标题、用户信息或完整 URL。

**验收条件**

开关对应真实功能，并在隐私说明中准确列出记录字段、保留时间、容量限制、查看方式与清除方式；否则不对用户展示。

### P1-6：规则作用域允许创建当前没有消费者的组合

**静态证据**

设置页允许“视频标题”规则选择“视频页”作用域；规则引擎也把 `related` 视频卡片映射到 `video` 作用域，但 v0.1.4 的视频页适配器只扫描评论和弹幕，没有扫描相关视频卡片。

另外，动态页和空间页虽然在表单中可勾选，但明确标注为“后续”，当前没有适配器。

**实际后果**

用户可以创建并成功保存永远不会触发的规则，看不到错误提示。

**建议修复**

- 根据规则目标动态限制可选作用域；
- 未实现的作用域应禁用而不是允许保存；
- 或正式实现视频页相关视频卡片过滤，再开放 `video + video-title`；
- 导入时对无法执行的组合给出明确提示，不要静默接受。

**验收条件**

UI 中能保存的每一种目标/作用域组合都有真实运行路径和自动化测试。

### P1-7（工程侧已解决）：共享默认值与校验逻辑在多个构建文件中重复

**静态证据**

默认设置和状态校验至少出现在：

- `background/service-worker.js`
- `content/bootstrap.js`
- `options/index.js`

弹窗还内置了一份 `applyCleanModePreset`。

这应当是打包结果中的正常模块复制，但如果开发者直接编辑安装包，就必须人工同步多处。

**当前处理**

共享默认值与校验现由 `src/shared/` 单一维护，再由构建脚本组合到各运行入口。生成 bundle 中仍会包含必要的重复代码，但不再分别维护。后续仍建议在 GitHub Actions 中执行 `npm run verify`。

**验收条件**

一个共享源定义能够生成所有运行入口所需代码，任何状态字段变更只需要修改一处源码。

## 7. 需要在真实 B 站页面验证的问题

这些问题从代码看存在较高风险，但是否已经影响当前线上页面，需要浏览器实测和 DOM 样本才能最终确认。

### P1-V1：B 站 DOM 选择器是否仍然命中正确元素

重点检查：

- 新版 Web Component 评论：`bili-comment-thread-renderer`、`bili-comment-reply-renderer`、`bili-comment-renderer`；
- 旧版评论：`.reply-item`、`.root-reply-container`、`.sub-reply-item`；
- 首页卡片：`.bili-video-card`、`.feed-card`、`.video-card`、`[data-bvid]`；
- 搜索卡片：`.video-item`、`.video-list-item` 等；
- 播放量、时长、作者链接和用户等级字段；
- 新旧播放器弹幕开关。

必须确认过滤的是**最小正确边界**：不能只隐藏卡片内部的一层导致网格留下空洞，也不能错误隐藏包含多个卡片的外层容器。

### P1-V2：首页/搜索页隐藏后的布局回流是否稳定

历史上曾出现视频隐藏后排版错位的问题。v0.1.4 采用隐藏卡片元素并依赖 B 站原生布局回流，但正确性完全依赖卡片边界选择器。

实测至少覆盖：

- 首屏加载；
- 下拉加载新卡片；
- 刷新换一换；
- 登录与未登录首页；
- 搜索综合页和视频分类页；
- 窗口缩放；
- 卡片骨架屏变成真实卡片；
- 恢复本页内容后再重新扫描。

### P1-V3：低点赞评论能否稳定取得点赞数与发布时间

低赞过滤要求同时解析：

- 点赞数存在；
- 发布时间存在；
- 评论已超过宽限期。

当前时间解析只明确支持：刚刚、片刻前、N 分钟/小时/天/周/个月/年前、完整 `YYYY-MM-DD` 类日期。若 B 站显示“昨天”“前天”“MM-DD”“N 秒前”或把时间放在新属性中，`publishTimestamp` 会变成 `undefined`，低赞过滤便不会触发。

应采集脱敏 DOM fixture，覆盖所有真实时间格式，并优先采用稳定的数据属性而非展示文案。

### P1-V4：评论边界与楼中楼是否会误隐藏整串讨论

`commentBoundary` 会把部分 `bili-comment-renderer` 上提到 `bili-comment-reply-renderer` 或 `bili-comment-thread-renderer`。需要验证：

- 根评论命中时是否只隐藏预期的根评论及其回复；
- 单条楼中楼回复命中时是否只隐藏该回复；
- 是否会因为解析到第一个子元素而错误隐藏整个评论线程；
- 评论 DOM 更新后指纹是否重新计算。

### P1-V5：MutationObserver 和 Shadow DOM 全量遍历的性能

内容脚本在大范围 DOM 上监听 `childList`、`characterData` 和多个属性，并会递归扫描开放 Shadow Root。对于高频更新的首页和评论区，可能产生重复遍历。

需要使用 Chrome Performance/PerformanceObserver 测量：

- 首屏脚本耗时；
- 滚动时主线程长任务；
- 100、500、1,000 条评论时的扫描次数；
- 首页连续加载卡片时的 CPU 占用；
- 多个新增节点属于同一祖先时是否重复扫描。

目标应是按卡片/评论边界去重，并避免每次局部变化都重新遍历大块 DOM 和所有 Shadow Root。

### P2-V1：累计统计是否符合用户理解

当前统计的真实语义是“本次 DOM 生命周期中新隐藏的元素次数”：

- 同一元素只计一次；
- 同一内容如果被 B 站重新创建为新 DOM，可能再次计数；
- 虚拟列表复用同一 DOM 展示新内容时，可能漏计；
- `pagehide` 时异步上报不保证在所有关闭场景都完成。

需要决定对外文案是“过滤操作次数”还是“唯一评论/视频数量”，并据此设计稳定 ID、去重范围和持久化策略。

## 8. 过滤规则的真实执行顺序

### 8.1 评论

1. 用户白名单命中 → 显示，立即结束；
2. 用户黑名单命中 → 隐藏，立即结束；
3. 匹配自定义评论或作者规则；
4. 匹配当前模式启用的内置风险类别；
5. 应用 `@` 评论规则；
6. 计算广告、低信息量等质量信号；
7. 在发布时间可解析且超过宽限期时计算低赞信号；
8. 计算低等级信号；
9. 根据“弱信号必须组合”决定低赞/低等级是否可以触发；
10. 任何原因存在时，最终渲染层统一隐藏。

### 8.2 视频卡片

1. UP 主白名单命中 → 显示，立即结束；
2. UP 主黑名单命中 → 隐藏，立即结束；
3. 匹配标题或作者自定义规则；
4. 若能解析播放量，检查是否低于阈值；
5. 若能解析时长，检查是否低于阈值；
6. 任一原因存在 → 隐藏。

### 8.3 当前模式类别

| 模式 | 内置类别实际状态 |
| --- | --- |
| 轻度 | 辱骂、广告；关闭性相关、引战和低信息量 |
| 标准 | 辱骂、性暗示、性物化、性/关系羞辱、引战、广告；关闭低信息量 |
| 严格 | 标准模式全部类别，加低信息量；进入严格模式时还会开启低赞直滤，但切出时不会自动撤销，这是已确认缺陷 |
| 自定义 | 使用设置页中的类别开关 |

## 9. 规则引擎与内容识别的现有限制

这些不一定都是立即修复的 Bug，但下一位 AI 不能把当前能力描述得过强。

1. 内置类别词库非常小，属于保守 MVP，召回率有限。
2. 文本只做 NFKC、零宽字符清理、空白合并、大小写处理和三次以上重复字符压缩；对谐音、拆字、拼音、emoji 替换、形近字和复杂绕过处理有限。
3. 无上下文理解，可能无法区分引用、反驳、自嘲、讨论术语和真正攻击。
4. “完整词”使用 Unicode 字母/数字边界，对连续中文句子中的关键词可能不符合普通用户预期。
5. 正则验证只拦截少数明显嵌套量词，仍可能存在 ReDoS 风险；导入文件可带入用户界面未能创建的超长或高开销表达式。
6. 最多允许 2,000 条规则，每个候选元素会按优先级遍历规则；大量复杂正则可能明显拖慢页面。
7. 视频播放量或时长解析失败时采取“放行”，这是相对安全的默认值，但会造成漏过滤。
8. 评论点赞数或发布时间解析失败时，低赞规则不会完整生效；`@` 保留规则在点赞数缺失时则不会保留评论，这是更严格的行为。
9. 评论作者链接选择器较宽，含 `@` 的评论必须验证是否可能把被提及用户误当成作者 ID。

## 12. 对接手 AI 的工作与沟通要求

用户正在学习 GitHub，技术步骤应使用中文并写清：在哪个页面、点击什么、文件放哪里、运行什么命令、成功时看到什么。不要只说“提交 PR”“配置 CI”而不给具体操作。

处理代码任务时：

- 先说明准备修改哪些文件和为什么；
- 改动应尽量小，并围绕一个明确 Issue；
- 不要顺手加入云端 API、遥测、账号权限或额外站点权限；
- 不要扩大到动态页、空间页、OCR 或 AI 模型，除非用户明确要求；
- 每次修复都给出复现步骤、修改说明和测试结果；
- 对选择器适配，保存脱敏 DOM fixture，不保存真实用户名、评论内容或账号数据；
- 涉及隐私行为变化时，同步更新隐私说明；
- 涉及用户可见功能或默认值时，同步更新安装说明、README 和版本记录；
- 不要把“代码存在”当作“线上页面已验证”。

### 用户最看重的体验

1. 不误伤正常评论；
2. 命中后页面干净，不出现扩展提示；
3. 首页隐藏视频后排版自然回流；
4. 低点赞规则确实生效；
5. 设置直观、状态一致；
6. 本地隐私承诺可信；
7. 项目适合公开展示和长期维护。
